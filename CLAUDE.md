# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All tooling goes through mage, pinned as a Go tool dependency — nothing to install first.

| Command | What it does |
| --- | --- |
| `go tool mage` | Default target: vet, test, build |
| `go tool mage go:lint` | `go tool -modfile=lint.mod golangci-lint run` |
| `go tool mage go:race` | `go test -race ./...` |
| `go tool mage go:fmt` | `gofmt -l -w .` |
| `go tool mage go:dist` | Cross-build all five release targets into `dist/` |
| `go tool mage -l` | List every target |

Run all four of `go tool mage`, `go tool mage go:lint`, `go tool mage go:race`, and `go tool mage go:fmt` before considering a change done.

Targets under a namespace need their prefix. Mage's fuzzy matching will accept `lint` for `go:lint`, but the namespaced form is the real name and the one to write.

The `-modfile=lint.mod` is load-bearing: golangci-lint's dependency tree and its higher Go floor live in `lint.mod`/`lint.sum` so the daemon's `go.mod` stays tiny and keeps its lower floor. Plain `golangci-lint run` is not the project's way.

Single test: `go test ./internal/keeper -run TestName -v`. Mage has no single-test target.

`TestManualDiscovery` hits the real network and is skipped unless `HUE_MANUAL=1` (optionally `HUE_ADDRESS=<ip>`).

## Style

- Prefer the standard library. The daemon depends only on `gopkg.in/yaml.v3`; a well-justified new dependency is fine, but reach for stdlib first.
- Tests use stdlib `testing` and `httptest` only — no testify or other assertion libraries.
- Commit directly to `main`; no branch or PR workflow.

## Invariants

These encode real failure modes. Changing them needs deliberate thought, not a refactor.

- **The 10s recall floor is not configurable.** `config.MinRecallFloor` silently raises any lower non-negative `min_recall_interval`; a negative one is rejected by `validate` instead, so it is named rather than arriving downstream as a legal-looking ten seconds. It is the last defence against a recall → light-on event → recall feedback loop. `TestDoesNotLoopWhenRecallTurnsOnWholeRoom` (driven by `fake.Bridge.EchoOnRecall`) is the regression test for exactly this; if suppression logic changes, it must still pass.
- **Suppression is armed before the recall request is sent**, not after — the bridge starts turning lights on the moment it accepts the recall. It is rolled back on *any* failure, including a timeout where the bridge may in fact have applied the recall. Keeping it armed there looks safer but strips the room of its recovery: the recall floor that `rollback` also restores is what blocks that recall's own retry. The echo a timed-out recall produces is covered by `recall_cooldown`, which is shorter than the request timeout that got us there. The one exception is `shutdown`: a recall still on the wire when `drainGrace` runs out keeps its window armed and is never rolled back. That is safe for exactly one reason — the Keeper is being thrown away. `Run` returns immediately after, and `cmdRun` either exits or builds a fresh Keeper with fresh maps, so nothing that outlives the drain reads that state. It stops being safe the day a `Keeper` is reused across a stream restart.
- **Suppression is armed on every group the echo can be attributed to, not just the recalled one.** The bridge lights the whole group and reports each light as newly on, and those events resolve back through the same exclusion-aware `GroupForLight` that attributed the trigger — a light's non-excluded room first, then its zones. Using the *same* resolution for trigger, echo and arming is what keeps this invariant true by construction; arming with a different predicate than the echo resolves under reopens the fan-out. For a room recall the set is a singleton, and so it is for a zone that only carves lights out of excluded rooms. For a mixed zone it is not: the zone wins only for a light in no live room at all, so a zone blending such lights with room-owning ones sends its echo into those rooms — where, with no window of their own, every one of them scheduled a recall off the back of ours. `TestACarveOutZoneRecallDoesNotFanOutIntoLiveRooms` covers the carve-out flavour. `armSuppression` walks `LightIDsInGroup` and arms the distinct set, and `rollback` must undo exactly that set; do not collapse either back to a single group. `lastRecall` is deliberately *not* written for the extra groups: it is the floor on how often a room may be restyled, not an echo filter, and a room must not lose its next ten seconds because a zone it lends a light to was recalled. `rollback` tells its own window from a newer one by comparing the stored deadline against `armedUntil`. That is a heuristic, not a refcount — two overlapping zone recalls that share a room and both fail can leave that room suppressed for up to one `recall_cooldown` — and the residue is bounded and far smaller than the fan-out it replaced.
- **Activity extends a pending recall but never creates one.** `kindActivity` is emitted for every light event that is *not* an off→on edge, and `schedule` only ever uses it to push out a deadline for a group already in `pending`. That asymmetry is the whole reason a recall's own echo cannot feed itself: by the time the bridge reports the lights the recall turned on, `drain` has already removed the entry that caused them, so there is nothing to extend and activity cannot conjure a new entry. If you ever let activity create an entry, `TestDoesNotLoopWhenRecallTurnsOnWholeRoom` is what will tell you.
- **`coalesce_window` is an idle gap, not a fixed window.** It is what stops the daemon writing a scene into the middle of another automation's whole-house burst. The late half of such a burst arrives at lights the scene has already turned on, so it carries no off→on edge and would never trigger a correcting recall — the room would just stay half-styled. `coalesce_max` caps the deferral so a chattering light cannot starve its room — but only within one round of coalescing. An entry deferred in `drain` because its group's previous recall is still on the wire carries `hardAt` forward, so `coalesce_max` is not a ceiling on the total time a group can stay pending. That is a deliberate, documented trade (#2, closed won't-fix): leaving `hardAt` behind would strand `fireAt` past it and make `extend` a permanent no-op for that entry, so it would fire one window after the recall ahead of it lands, in the middle of a burst that is still going — the half-styled room this whole mechanism exists to prevent, and not a rare shape, since a burst is what puts a recall on the wire to begin with. The overrun costs one round trip per deferral, and since an excluded light no longer emits activity it cannot contribute to it. `TestActivityInAPendingRoomDefersTheRecall` is the regression test.
- **The debounce runs on `schedNow()` (real time), not the `k.now` test hook.** Its deadlines are waited out by a real `time.Timer`, so the two clocks must agree. `k.now` stays the *policy* clock — the recall floor and the suppression window — which is the part tests move by hand. Putting the debounce on `k.now` strands every pending entry the moment a test freezes it.
- **Recalls are sent from the `sender` goroutine, but every decision stays on dispatch.** `commit` runs the floor check and arms suppression, the sender only performs the HTTP request, and `finish` handles the answer — so `suppressUntil`/`lastRecall`/`inFlight` are still single-goroutine state with no locking. The split exists so a slow bridge delays one room instead of freezing the scheduling of every room behind it. `inFlight` is what stops a second recall for a group stacking behind one already on the wire. The sender deliberately outlives the caller's context: `Run` gives it `context.WithoutCancel(ctx)` and cancels it only once dispatch has returned, because the shutdown drain's requests are the sender's and tearing it down with everything else would abandon the very work the drain exists to finish. The teardown order `stopWork(); <-dispatchDone; stopSending(); workers.Wait()` is therefore not arbitrary, and `dispatchDone` is closed by a defer registered inside the worker function so it fires as a panic unwinds too — otherwise a dead dispatch goroutine leaves `Run` waiting for a drain that will never happen.
- **A stop drains the recalls dispatch is holding, bounded at `drainGrace` (3s).** `dispatch`'s `ctx.Done()` path calls `shutdown`, which commits every pending entry oldest-`seq` first — the room you walked into first is styled first — then reads `k.results` until `inFlight` empties or the grace period expires, and logs what it could not finish. Dropping those entries instead loses them for good: the light that caused the recall is already on, so the next start's resync sees it as it has always been and no off→on edge ever occurs, and `onConnect`'s first-connect branch has no earlier state to diff against. The room keeps whatever the last automation left it in until somebody flips a switch by hand, and a `systemctl restart` or a package upgrade landing seconds after someone walked into a room is exactly that window. The drain changes no decision-making: it runs on the dispatch goroutine like everything else, `commit` still applies the recall floor and the "is any light still on" veto, and the `inFlight` guard still refuses to stack a second recall on a group whose first is on the wire. Three seconds is chosen to sit well inside systemd's 90s `TimeoutStopSec` and launchd's 20s and to be short enough that nobody watching a restart learns to reach for `kill -9`; a bridge that has stopped answering costs the whole of it, once. `TestSIGTERMSendsTheRecallItWasHolding` and `TestASecondSignalQuitsMidDrain` are the regression tests.
- **A panic on one of `Run`'s goroutines is logged and then re-panicked, never absorbed.** `logPanic` names the goroutine and dumps the stack through the daemon's own logger, then lets it carry on unwinding. Swallowing it would leave the process alive and quiet with no dispatch goroutine — deciding no recalls at all — or a lookup worker dead mid-item with its group marked busy forever, so that room never gets another power-restore lookup. Dying is what gets the service manager to restart us, which is the same reasoning as `Stream` giving up rather than retrying forever. The `workers.Done()` defer is registered before `logPanic`'s so the `WaitGroup` is still released as the re-panic unwinds. `runLookup` also checks `ctx.Err()` at the top of each item, so a worker stops walking a group's lights on behalf of a dispatch goroutine that has gone.
- **`exclude.rooms` and `exclude.lights` mean different things, and group exclusion is an input to attribution, not a veto after it.** An excluded *room* is never recalled at all **and cedes its lights**: `GroupForLight` takes an exclusion predicate, skips an excluded room, and falls to the light's first non-excluded zone — nothing at all if there is none. This is the carve-out pattern (a zone over just the lights you want styled, its own Natural Light scene, the room excluded) and it is deliberate that the resolver never returns an excluded group, so no downstream code checks `GroupExcluded` after resolving a light; the sites that still check it start from a group, not a light. Two consequences are load-bearing. First, `enqueueStartupTriggers` must spend a group's one startup trigger only on a light that group *governs* — a zone's list is mostly room-owned lights, and the zone's iteration is the only one that ever sees a ceded light, its room being skipped as excluded (`TestStartupSpendsAZoneTriggerOnALightItGoverns`). Second, the config layer judges whether excluding a group does anything with the group's *own* exclusion peeled off (`allShadowed`'s except-self predicate): judged under itself every excluded group reads shadowed and the whole list would warn. An excluded *light* never triggers a recall **and never defers one** — `emitActivity` drops it before it reaches the queue — but is still lit when another light in its room causes one. The deferral half was a deliberate call, not an oversight to restore: the light people exclude is usually the one that will not sit still, so letting its chatter extend the wait held its room at `coalesce_max` for as long as it went on, and the single setting offered to silence it left it setting the pace instead. `TestExcludedLightActivityDoesNotDeferTheRoom` is the regression test. Do not collapse these. `groupForLightLocked` returns no group for a light the registry no longer holds, *before* the `lightToZones` fallback: a deleted light lingers in its zone's `Children` until the zone itself updates, so resolving through that stale mapping made the zone read as reachable and silenced the "exclusion has no effect" warning for an exclusion that had in fact stopped meaning anything.
- **There are two trigger sources, not one.** Off→on edges miss the mains-power case: when a lamp loses power while the bridge stays up, the cached state still reads "on", so no edge occurs. Zigbee connectivity returning to `connected` is the only signal for that, and it has a floor. The exemption a `power_restored` trigger carries from `commit`'s "is any light still on" veto is sticky on the pending entry (`foldedPowerRestore`), because the lookup deliberately never writes the returning lamp back into the registry — reading it off whichever reason created the entry meant a restore folded into an ordinary switch-on was silently vetoed and dropped. A mains cut only triggers a recall if it lasted long enough for the bridge to mark the lamp unreachable, which takes about a minute; a shorter cut produces no event at all. Measured on a real bridge: a ~10s cut leaves `on: true` and `status: connected` unchanged throughout, so both triggers are blind to it; a 2-3 minute cut works end to end. Polling would not close the gap — under that floor the bridge's own model of the lamp never moves, so there is nothing to poll for. This is an accepted limitation; say so plainly in user-facing text rather than promising that a power cycle always triggers a recall.
- **`registry.Sync` skips one unusable resource but fails on a wholly unusable type.** A single entry the daemon cannot decode used to fail the sync, which fails `Resync`, which drops the stream — and the same resource comes back on the reconnect, so the daemon settled at the backoff cap, connecting and dropping forever while doing nothing at all. One bad entry is now warned about and dropped. Failing when *every* entry of a type was unusable keeps a shape change loud, since carrying on there would leave the cache quietly empty of a whole class of resource; the hole that leaves is a type holding exactly one entry, where an unusable entry still fails the sync, and that case is genuinely indistinguishable from a shape change. HTTP and envelope errors still fail the sync outright, and on any failure the old cache is kept rather than half-replaced. A resource with no `id` counts as unusable on the sync path as well as the stream path — caching it files a zero value under the `""` key, where `Group("")` and `SmartScene("")` then report it as found.
- **`hue.Client` deliberately has no `http.Client.Timeout`** — it would cap the long-lived event stream. Per-request deadlines come from context: `do()` derives one from `Options.RequestTimeout` (10s default), and `Stream` deliberately does not go through `do()`. The deadline starts **after** `lim.wait` returns, not at entry — starting it at entry would spend most of the budget queueing and time out requests that were never sent.
- **CLIP v2 reports most application failures inside a 200, so `Retryable` has two refusal types, not one.** A `*StatusError` is classified by its code; an `*EnvelopeError` — a populated `errors` array in a 2xx body — is never retryable. Without that second type a scene deleted in the Hue app reached `Retryable` as a plain error, fell through to "transient", and was recalled again through the whole of `recallBackoff`. The bridge offers no machine-readable code to sort these by, only a description whose wording is not part of any contract, so the trade is deliberate and one-way: a genuinely transient condition delivered this way (a lamp briefly unreachable) is now surfaced once rather than retried. Anything that is neither of those two and not the caller's own cancelled context is still transient by default. `Pair` returns an `*EnvelopeError` for the same reason — it is what stops `PairWithRetry` polling out the rest of the window against a bridge whose whitelist is full.
- **The stream watchdog is armed before `c.http.Do`, not after it returns.** Nothing else bounds the wait for response headers — no `Timeout`, no `ResponseHeaderTimeout` — so a bridge that completes TLS and then never answers would block in `Do` forever with the watchdog not yet running. `TestStreamWatchdogArmedBeforeRequest` is the regression test.
- **One event-stream frame is capped at `maxFrameBytes` (8 MiB), and lines are read with `ReadSlice`, not `ReadString`.** `bufio.NewReaderSize` sets only the *initial* buffer and `ReadString` grows without bound, so a peer that sends bytes and never a newline could allocate until the daemon is OOM-killed; `ReadSlice` fails with `ErrBufferFull` instead of growing, which is what makes the accounting possible at all. A per-line cap alone does not bound a frame built from many `data:` lines that never sees its terminating blank line, so `streamOnce` caps the accumulation too. `errFrameTooLarge` is retryable on purpose: the frame is abandoned, the connection recycled, and `onConnect`'s resync is what puts the caller back in step. 8 MiB is orders of magnitude above a whole-home update, so a real bridge never approaches it.
- **The transport sets `ForceAttemptHTTP2: false` deliberately.** The watchdog recovers a wedged bridge by cancelling the request context, which under HTTP/2 only sends `RST_STREAM` and returns the TCP connection to the pool — so the reconnect opens a fresh stream on the same dead pipe and recovers nothing. Under HTTP/1.1 cancelling closes the connection, which is what the watchdog means. `TestStreamWatchdogOpensANewConnection` counts accepted connections and fails if h2 is re-enabled. Note `httptest.NewTLSServer` is HTTP/1.1 only, so a test must set `EnableHTTP2` explicitly to exercise this at all.
- **`Stream` returns rather than retrying forever on errors retrying cannot fix.** A revoked application key (403) or an `ErrPinMismatch` ends `Run`, so the service manager sees a failure instead of a process that is alive, logging retry warnings, and doing nothing. `Retryable` returns false for `ErrPinMismatch` for the same reason. A watchdog teardown counts as a *failure* even though the connection was open the whole time — otherwise the uptime check resets the backoff and a mute bridge is retried at full speed forever. That uptime threshold is `StreamOptions.HealthyConnection`, per-stream rather than a package variable, because a package variable is shared state one test writes while another test's still-running `Stream` goroutine reads it. For any of that to reach the caller, `Run` has to cancel its own goroutines rather than wait for the caller's context to do it: dispatch and the lookup workers run on a `workCtx` derived from `ctx` which `Run` cancels once `Stream` has returned. Without that they watched only the caller's context, so a `Stream` that returned on its own left `Run` blocked on them forever and the error never arrived — the alive, quiet, recalling-nothing process this invariant exists to prevent, with the rediscovery below unreachable behind it. `TestRunReturnsWhenTheStreamGivesUp` is the regression test.
- **After `MaxConsecutiveFailures` the stream gives up with `ErrStreamUnreachable` and `cmdRun` rediscovers the bridge by id.** A bridge whose DHCP lease moved is never coming back at the old address, and that address is re-read from the credentials file on every restart, so retrying it was unrecoverable without hand-editing JSON. An address set with `--address` or `bridge.address` is never overridden by discovery.
- **Bracketing an IPv6 literal for a URL happens in `hue.hostPort`, and only there.** `net/url` reads `https://fe80::1/...` as a host of `fe80:` on port 1, which surfaces as an error about a port the user never wrote. `hostPort` is idempotent and returns hostnames, IPv4 literals and addresses that already carry a port or brackets unchanged, so it is safe to apply at every point a URL is built: `Client.url`, `probe`, and `discoverCloud`'s portless branch. `config.CleanAddress` must *not* also bracket — it validates, and its output round-trips through `credentials.json` and back into itself on every start, so bracketing there breaks that round trip *and* composes into `[[...]]` here. A zoned literal like `fe80::1%en0` is still left unbracketed, because `net.ParseIP` rejects zones; that is a known gap, not a decision.
- **`go:build`, `go:dist` and `pkg:build` all compile with `CGO_ENABLED=0`, and the systemd unit's `RestrictAddressFamilies` is why.** A cgo build resolves hostnames through glibc's `getaddrinfo`, which opens an `AF_NETLINK` socket the unit does not allow, so cloud discovery failed under the unit on a host where DNS demonstrably worked — while the same source built by hand worked fine. The two settings are coupled: loosening one means loosening the other.
- **TLS pinning is trust-on-first-use** over the bridge's SubjectPublicKeyInfo and fails closed on mismatch, and the check runs once per *full* handshake, not once per connection. The client keeps a `ClientSessionCache`, and Go does not call `VerifyPeerCertificate` on a resumed handshake — it restores `PeerCertificates` from the session instead. That is still fails-closed: only a peer holding the master secret of a session we already pinned can resume one, so a replaced bridge or an impersonator can only offer a full handshake, which runs `Pin.verify`. Trust-on-first-use is untouched, because the first handshake of a process is always full. The cache is there because without it every connection is a full handshake and `IdleConnTimeout` (90s) is far shorter than the gap between one room's recall and the next, so the pool is nearly always cold and that handshake lands on the critical path of a user-visible event — on a bridge slow enough for it to matter. It is set outside the `!o.Insecure` branch deliberately; the two are orthogonal. `TestClientResumesTLSSessions` guards the wiring and `TestPinStillFailsClosedWhenSessionsResume` guards the argument above. `hue.Options.Insecure` disables pinning and is test-use-only. `Pin.verify` deliberately does **not** hold `p.mu` across `OnLearn`. The callback runs on the TLS handshake goroutine and is expected to do an fsync'd write, so holding the lock `Value()` takes across it deadlocked any callback that read its own pin — mid-handshake, with nothing to time it out. A second mutex, `p.learning`, keeps the learn-exactly-once guarantee instead: whoever takes it re-reads `p.value` and falls through to an ordinary match if another handshake learned while it waited. What that buys the caller is a real contract — `OnLearn` may read `Value()` and may take as long as a durable write needs — with one prohibition: it must never drive a fresh handshake against the same `Pin`, which re-enters `verify` and is the one thing `learning` cannot let through. It must also genuinely persist, because the pin is committed to memory only when it returns nil; a callback that merely sets a field satisfies the signature and not the promise. `TestPinDoesNotHoldItsLockAcrossOnLearn` and `TestPinLearnsOnlyOnceUnderConcurrentHandshakes` are the regression tests.

## Gotchas

- Pairing must run as the user that runs the service. Credentials default to `$XDG_STATE_HOME/hue-scene-keeper/credentials.json` (mode 0600, written via CreateTemp+rename with both file and dir synced). The systemd unit passes `--config`/`--state` explicitly rather than relying on XDG, because `auth` run as the service user would otherwise write to that user's home and the service would read a different file. `auth` writes the pin the instant it is learned rather than with the rest of the credentials at the end: the handshake that learns it happens on the first pairing attempt, minutes before the user gets round to the link button, so giving up, Ctrl-C or a closed laptop used to leave that process trusting a certificate nothing had recorded and the next run walking back into the trust-on-first-use window with nothing said. Both callers share `persistPin`, which writes `creds.Address` too, so an `auth --reset-pin --address <other bridge>` abandoned before the link button leaves the old `app_key` beside the new address and pin. That was a conscious trade: it is a deliberate re-pair, a successful one rewrites all three fields, and `Credentials.Save` refuses to write a blank `AppKey` over an existing one — so the residue is a stale key next to a bridge it does not open, and running `auth` through to the end is the fix.
- In config, **zero means "default", never "off"**, and a negative is an error. There are no pointer fields, so an absent key and one written `recall_cooldown: 0` arrive identically and cannot be told apart; filling both is the only consistent reading. A negative is unambiguously a mistake, and this is the package that refuses every other unambiguous mistake. Turning a knob off would need pointer fields and is deliberately not offered.
- The config file is entirely optional — a missing file is not an error. `keeper.New` falls back to `config.Default()` on a nil config for the same reason: those are the very settings a missing file yields, and the alternative was a nil dereference on the dispatch goroutine seconds later, on a stack that says nothing about who built the Keeper.
- `magefiles/` carries a `//go:build mage` tag, which is why `.golangci.yml` needs no exclusion for it.
- The launchd plist in `deploy/` needs no templating: it runs the daemon under `/bin/sh -c` so `$HOME` expands in the user's own session, which is the only way a system-wide plist in `/Library/LaunchAgents` can reach a per-user log path.
- In the pkg postinstall, `launchctl enable` must run **before** `launchctl bootstrap`. A label in launchd's per-user disabled database makes bootstrap fail with `Bootstrap failed: 5: Input/output error`, and that database outlives the plist, so enabling afterwards never recovers. Check with `launchctl print-disabled gui/$(id -u)`. All four places that bootstrap now enable first — the postinstall, `service.Start`, the README's manual install, and the plist header — and `Pkg.Uninstall` re-`enable`s the label on its way out, before deleting the plist: `hue-scene-keeper stop` is `launchctl disable`, so that entry would otherwise outlive the package and fail a later install by hand with nothing on disk to explain it. The postinstall's `bootstrap` also retries three times with a second between attempts: `bootout` of a running agent is not synchronous, so installing over one could lose the race and fail the whole package on a transient error 5.
- The second `SIGINT`/`SIGTERM` force quits. `signal.NotifyContext` cancels on the first signal but its goroutine then stops listening while leaving the `Notify` registration in place, so the default disposition stays disabled and a second Ctrl-C does nothing until the process exits on its own — which is how people learn to reach for `kill -9`. `signalContext` keeps receiving and exits `128+signal`. Its channel is buffered 2 deliberately: with a buffer of 1 the second signal is dropped if it lands while the goroutine is between receives, which is the bug being avoided. Since the shutdown drain this is load-bearing rather than a courtesy — the first signal can now block for the whole of `drainGrace` against a bridge that has stopped answering, and the force quit is what makes a blocking shutdown acceptable at all. It runs on its own goroutine, so a drain that is stuck cannot swallow it.
- `cmd/hue-scene-keeper`'s tests re-execute the test binary as the daemon: `TestMain` hands its own argv to `main()` when `HUE_SCENE_KEEPER_TEST_DAEMON=1` and returns before `m.Run`, so no test flag is ever parsed. Signals are the subject there — what a SIGTERM finishes and what a second one cuts short — and neither can be observed from inside the process being signalled. Arguments ride on argv rather than the environment so the daemon parses exactly what a shell would have handed it. Stdlib only; it adds no dependency.
- Exit statuses are part of the CLI's contract. An error implementing `ExitStatus() int` sets the process status and its message is *not* printed, because the command has already said its piece: `status` returns 3 (the LSB code for "not running") after printing its verdict in words, and a flag parse error returns `silent(1)` because `flag.ContinueOnError` has already printed both the message and the usage block. Only `run` unwraps `context.Canceled` to exit 0 — signalling the daemon is how it is stopped; for the interactive commands the same error means the work the user asked for did not happen, and a script running `auth || exit 1` has to hear about it.
- `PairWithRetry` polls through transient failures now, and only stops on a refusal that will not change on its own or on ctx ending. The pairing window is the two minutes in which the user is standing at the bridge pressing its button, so a 503 from a busy bridge is the likeliest error there is and giving up on one cost them the whole ceremony. Consequence worth knowing: after a transient error its give-up message wraps that error rather than `context.Canceled`, so an interrupted `auth` no longer exits 0 silently — `cmdAuth` checks the outer ctx itself and says so plainly.
- Run `go tool mage go:install` as yourself, never under `sudo`. Only the two `install` calls are elevated, through the same "sudo if not root and sudo exists" probe `internal/service` uses; the compile deliberately stays unprivileged, because `sudo -E` preserving `HOME` leaves root-owned entries in the build and module caches that every later non-root build then fails on. Note that `install -d -m0755 /usr/local/bin` is not a no-op on an existing directory: on a group-writable `/usr/local/bin` (a multi-admin Homebrew machine) it silently strips group write. The guarded `[ -d ] || install -d` form the postinstall uses would be the safer shape.
- **The macOS log cap is in-process (`internal/logfile`), and newsyslog was rejected for concrete reasons.** The log lives at a per-user `$HOME` path that one root-owned `/etc/newsyslog.d` rule cannot name without the `G` glob, newsyslog rotates by rename, and it finds the process to signal a reopen through a pid file — which a launchd-managed per-user agent does not have. Without that signal the daemon's inherited descriptor follows the rename into `.1`, so the live file stays empty, `tail` shows nothing, and the space is never reclaimed because the archive is deleted out from under an open descriptor. It would also need `pkg:build` to place a file outside the package's own prefix, leaving manual installs uncapped. `logfile.Write` checks the size *before* writing so a record is never split (slog calls `Write` once per line); `rotate` renames first and keeps the old handle until the new file is open, so no failure path leaves the daemon with nothing to log to; and it reports no error, because `slog` discards what a handler's `Write` returns — a failed rotation resets the counter instead, deferring the retry by a cap's worth of bytes rather than issuing a failing syscall per line. The size is seeded from `Stat` at open: starting from zero means an unpaired daemon, which launchd restarts every 30s, appends a fresh cap each time and the limit never binds. The plist keeps its `>>` redirect alongside `--log-file` — it is what catches runtime panic stacks and the errors `main` prints before a logger exists — so those bytes are uncounted and land in `.1` after a rotation. Both are deliberate. User-facing text must say `tail -F`: `-f` follows the inode onto the archive and goes quiet.

- A light switched on during the initial ~1.5s startup resync is missed, and this is accepted. The opening GET already reports it as on, so no off→on edge ever occurs, and `apply_on_startup` is off by default. Reconnects do not have this hole — `onConnect` diffs lit lights before and after the resync — only the very first connect does, once per daemon lifetime, over a window the user would have to hit by hand. Closing it would mean recalling on state the daemon never saw change.
